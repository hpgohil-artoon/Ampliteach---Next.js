Headline finding

This .claude/ folder belongs to a different project. It was written for a React + Vite ERP platform with react-router, TanStack Query, an erp-ui component kit and roughly 500 CRUD screens. Ours is a Next.js 16 App Router marketing site with 8 pages and no backend of its own. The rules contain 114 references to Vite / react-router / ERP internals and one passing mention of Next.js. Every internal doc link in it — PROJECT_STRUCTURE.md, ROUTING.md, CODE_QUALITY.md, RBAC_IMPLEMENTATION.md, ESLINT_SETUP.md — points at a file that does not exist here.

PART 01

The four config types, and when each one fires

You have four different mechanisms in that folder and they load at completely different times. Knowing which is which is most of knowing how to use them.

TypeLives inWhen it loadsUse it for
CLAUDE.md CLAUDE.md
.claude/CLAUDE.md		 Every session, automatically, before you type anything The short, always-true facts about the project: stack, structure, conventions, the commands that must pass. Keep it small — you pay for it on every single turn.
Rules .claude/rules/*.md Only when read. Not automatic — they load because CLAUDE.md tells me to open them Deep standards too long for CLAUDE.md. A pointer in CLAUDE.md plus the detail in the rule file. Good pattern, and the one your ERP project is using.
Skills .claude/skills/<name>/SKILL.md On demand — you type /name, or the description matches what you asked for Repeatable procedures: "scaffold this", "set up that", "write the MR description". Only the one-line description is always in context; the body loads when triggered.
Agents .claude/agents/*.md When explicitly asked, in a separate context Work you want done without its file-reading filling up your main conversation. A reviewer, a searcher. It reports back a conclusion.

The distinction that matters most

A rule is a constraint; a skill is a procedure. A rule says "never use any" — it applies to everything you do, forever. A skill says "here is how to set up commitlint" — you invoke it once and it's done. If you find yourself writing a rule that begins "when the user asks…", it's a skill. If you write a skill that says "always…", it's a rule.

The cost nobody mentions

Context is finite, and CLAUDE.md is spent first. Here is what this folder currently costs:

File setSize≈ TokensLoaded
.claude/CLAUDE.md69 KB~18,000Every session, unconditionally
rules/ (8 files)342 KB~87,000Whenever CLAUDE.md's "MANDATORY — read before any change" is obeyed
skills/ (17)909 KB~233,000Only the triggered one — descriptions always resident

So before a single line of your code is read, ~18k tokens of another project's architecture is already in context — and following its own instructions would pull in ~87k more. That budget is better spent on your actual files.

PART 02

Where it contradicts what we built

Not a style difference. These are instructions that would produce broken code in a Next.js App Router project.

1 · page.tsx means the opposite thing

Their CLAUDE.md: "page.tsx is a thin route entry… it imports that component, optionally applies the withPageHeader HOC, and default-exports." That's a react-router leaf module.

In Next.js App Router, page.tsx is the route — its position in the folder tree defines the URL. There is no withPageHeader, no react-router, no createBrowserRouter.

2 · The folder structure is a different one

It mandates src/app/, src/modules/, src/shared/, src/lib/, src/core/ with a strict one-way import graph — enforced by their ESLint config.

Ours is app/ components/ features/ content/ lib/ hooks/ types/ config/. Their eslint-setup skill would fail our entire src/, and src/app/ means "the router" to us and "the composition root" to them.

3 · Components that don't exist here

Four rules mandate imports from @/shared/ui/erp-ui, @/shared/ui/form, @/shared/table, @/shared/modal, @/shared/storage, @/core/utils — ErpButton, ErpViewField, DataTable, modalService, displayDate.

None of them exist in this repo. We use shadcn/ui in components/ui/. Following those rules produces imports that don't resolve.

4 · Patterns for features we don't have

The rules cover data tables with collapsible group subtotals, file uploads with presigned S3 URLs, RBAC permission gating, PATCH envelope semantics, editable grids, and a modal registry.

Our site has zero tables, uploads, auth, and modals. Login is a link to app.ampliteach.com — a separate product we don't touch.

Two CLAUDE.md files that disagree

There are currently two, and both load:

CLAUDE.md              → @AGENTS.md — Next.js 16's own generated guidance.
                         Correct for us. Re-created by `next dev`, so leave it.
.claude/CLAUDE.md      → 69 KB describing a React Vite ERP platform.
                         Wrong for us, and 3.8× larger than everything else combined.

One says "this is Next.js 16, read the version's own docs before writing code". The other says "this is a React Vite ERP, put screens in src/modules/". They cannot both be followed.

On your TypeScript reminder

Already handled, and it's the one place this folder and our project agree. The project is TypeScript with strict: true, tsc --noEmit is wired as npm run typecheck inside npm run verify, and it currently passes clean. typescript-rule.md is the single rule in that folder worth keeping — see Part 03.

PART 03

All 8 rules

What each one governs, and whether it survives the move to Next.js. Sizes matter here — the top two are 190 KB between them.

RuleSizeWhat it's forVerdict & why

Keep — 2 edits The only genuinely stack-agnostic rule in the set, and it matches how the project is already written. Fix: its import example shows react-router-dom and @/modules/..., and it says npm run type-check — ours is npm run typecheck.
eslint-rule.md 18 KB "Zero ESLint errors, always" — run npm run lint, never infer it from a passing tsc, never eslint-disable. Plus kebab-case naming, layer boundaries, barrel-only and absolute imports. Keep the principle only The discipline is excellent and worth adopting verbatim — it's already in our npm run verify. theme-and-ui-rule.md 10 KB Every visual change must be theme-aware — no hardcoded colours, use theme tokens — and must reuse the @/shared/ui/erp-ui kit rather than hand-rolling components. Remove The underlying principle is one we already follow: colours come from tokens in globals.css, components from components/ui/. But the rule enforces it by naming a component kit that isn't here. form-fields-rule.md 108 KB The single largest file. Governs every input in the ERP: which adapter to use, zod-derived required asterisks, caps reported not applied, GSTIN/pincode/mobile formats, editable-grid cells, country→state cascades. Remove Deeply impressive and completely inapplicable. It mandates @/shared/ui/form adapters, NUMERIC_FIELD_LIMITS, useFieldLimitError, ErpEditableGrid — none of which exist here. api-integration-rule.md 82 KB Four-layer data flow — Component → hook → query → api → backend — with TanStack Query key factories, full PATCH payloads, orNull semantics, backend-authored toast messages. Remove Assumes a live REST backend with mutations. We have no runtime API: it's a static site, content is fetched at build time through src/lib/api/, and there are no mutations at all. The layering idea is sound and we already apply a simpler version of it.
data-table-rule.md 42 KB Two table engines picked by data shape, shared toolbar/filter/pagination pieces, per-column aggregation, group subtotals, plus the app-wide date and empty-value display helpers. Remove The site has no tables, grids or lists of records — the closest thing is a 6-card blog grid. 42 KB for a feature the project doesn't contain.
file-upload-rule.md 66 KB One shared storage service, upload-on-pick, presigned-URL reads, a single preview component, blocking Save while an upload is in flight. Remove Nothing on this site uploads a file. Static export has no server to upload to.
modal-rule.md 8 KB All confirm/delete prompts go through modalService.open(ModalType.CONFIRM, …); typed FORM / DRAWER / PREVIEW variants; a registry for domain modals. Remove We have one Sheet — the mobile nav drawer — and no confirmations, because there is nothing destructive to confirm.
Worth saying plainly

These rules are good work. The 108 KB form rule documents real bugs with the incident attached — a whitespace-only value satisfying a required field, a date arriving a day early because someone called .toISOString() on a picker value. That's institutional knowledge worth having. It just belongs to the ERP repo, where those components exist and those bugs happened. Keeping a copy here doesn't help that project and actively misleads this one.

All 17 skills

Skills are cheaper to keep than rules — only the description stays resident. But a skill that fires on a Next.js project and starts installing Vite plugins is worse than no skill.

PART 05

The agent

One agent, and it's the easiest call in the audit.

agents/code-quality-reviewer.md · runs on Haiku

What it's for: you hand it specific file paths and it produces a compliance report — per-file status, standards met, issues with severity and recommendation, an overall score and an APPROVED / NEEDS REVISION verdict. It runs in its own context, so reading all those files doesn't consume your main conversation.

Why it can't work here: its entire method is "review the complete docs/CODE_QUALITY.md document to understand all applicable standards" — and it's told to cite specific sections when reporting a violation. docs/CODE_QUALITY.md does not exist in this repo. It would either fail immediately or invent standards to review against, which is worse than not reviewing.

Verdict: Remove — but the idea is good and worth rebuilding later against a real standards file. Meanwhile the built-in /code-review command does the same job with no setup, reviewing your actual diff.

Also worth knowing

.claude/settings.local.json is yours — it's the growing allowlist of commands you've approved me to run without asking (npm, shadcn, the site fetches). Leave it alone; it's working as intended. settings.json is the shared one, and it currently just enables the skill-creator plugin.

  1. Replace .claude/CLAUDE.md — the single highest-value change. A Next.js version of it is roughly 2 KB, not 69 KB: our stack, our folder structure, the eight rules that keep files short, the static-export constraints, and the three commands that must pass.   2. Trim rules/ to one file. Keep typescript-rule.md with the two fixes from Part 03. Fold the "zero ESLint errors, never eslint-disable" discipline and the "no hardcoded colours" principle into the new CLAUDE.md as two lines each. Delete the other seven — that's 335 KB of another project's architecture gone.
  3. Trim skills/ to four. mr-description, commit-lint-setup, skill-creator, and logger-system-setup if you want it. Delete the other thirteen and all the *-workspace/ artefacts.
  4. Delete the agent, and use the built-in /code-review until there's a real standards file to point a custom reviewer at.
  5. Run commit-lint-setup. With npm run verify already green, a pre-commit hook makes the discipline automatic rather than remembered — which is exactly the class of problem your teamlead is trying to avoid.
  6. Later, write the skills this project actually wants. Once the brand pass and CMS wiring are done, the repeatable procedures here are things like add a new marketing page (route + section + content file + metadata + sitemap entry) and verify a static export before deploy. Use skill-creator to build them, in this repo, against files that exist.
Before I delete anything

Two things worth confirming with your teamlead first. One: was this folder copied in deliberately as a starting template, or by accident? If it was deliberate, the intent was probably "reuse our standards" — and the honest answer is that the standards transfer but the files don't, because they're written against components this project doesn't have. Two: this repo isn't under git yet. I'd rather git init and commit the current state first, so removing 140 files is a revertible commit instead of an irreversible delete. Say the word and I'll do it in that order.
