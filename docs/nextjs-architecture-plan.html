PART 02

Which rendering mode, and why

Four options, one sentence each — then the decision for every route. The short version: this site is static-first, with ISR on the three things that change.

SSG Static generation

HTML built once at next build and served from the CDN. Fastest, cheapest, cannot break at runtime because there is no runtime. Default in the App Router — you get it by not doing anything.

Use for: fixed marketing copy.

ISR Incremental Static Regeneration

SSG plus a timer or a webhook. Visitors always get a cached static page; Next rebuilds it in the background when it goes stale, so new content appears without a redeploy.

Use for: CMS-driven content. Needs a Next.js server.

SSR Server-side rendering

HTML rebuilt on every single request. Only justified when the output differs per visitor — logged-in dashboards, carts, personalisation.

Use for: nothing on this site. Slower and pricier for no gain.

CSR Client-side rendering

A 'use client' component that runs in the browser. Invisible to crawlers, so never for primary content — only for behaviour layered onto server-rendered HTML.

Use for: the six interactive leaves above.

PPR — not for this build

Partial Pre-rendering streams a static shell with dynamic holes punched in it. It is genuinely good, and it is genuinely still experimental — it needs next@canary and a Vercel-class runtime. It solves a problem this site doesn't have (no per-user content anywhere). Leave experimental.ppr off. Revisit in v2 if a logged-in area ever lands here.

Verdict

Static everywhere; ISR on pricing, the blog index, and posts; client components only on six leaves; SSR nowhere. Six pages of the site never touch a server at runtime, and the three that do serve cached HTML anyway.

Amended — S3 removes the ISR column

With static export as the target, ISR is not available: the three ISR rows above become plain build-time SSG. Pricing and posts are fetched from the CMS when next build runs and baked into HTML. The practical difference is who triggers the update — a CMS webhook must now hit the CI deploy pipeline instead of /api/revalidate. Everything else in the table stands, and the code is written so that setting NEXT_BUILD_MODE=server restores ISR with no source changes.

PART 03

The S3 problem — read this before anything else

Your teamlead's bad experience has a specific technical cause, and it is worth naming precisely, because it dictates the structure in Part 04.

A plain S3 bucket behind CloudFront serves files. It cannot execute Node. To deploy there you must set output: 'export' in next.config.ts, and that switch silently disables a long list of features:

FeatureWith a Node serverWith output: 'export' (S3)
SSG pagesYesYes
ISR / revalidate / revalidateTagYesNo — build-time only
SSR / cookies() / headers()YesNo
Route Handlers (app/api/*)YesNo — forms need an external endpoint
MiddlewareYesNo
next/image optimisationYesNo — needs images.unoptimized: true
Draft / preview modeYesNo
Clean URLsAutomaticNeeds trailingSlash: true + a CloudFront Function

Nearly every "Next.js deployment nightmare" is this list discovered late — code written against ISR and Route Handlers, then a build that fails or, worse, succeeds and serves stale pages and dead forms. The fix is not to pick a side now; it's to write the code so the side can be switched with config.

Hosting options, ranked

OptionGets youTrade-off
VercelEverything, zero config, ISR and webhook revalidation out of the box, preview URLs per branchNot AWS; per-seat cost. Best default.
AWS Amplify HostingFull SSR + ISR, managed, stays inside AWS and satisfies an "it must be AWS" mandateOccasional lag behind new Next releases. Best if AWS is required.
OpenNext (SST/CDK → Lambda + CloudFront)Full feature set on your own AWS accountReal infrastructure to own and debug.
Docker on EC2/ECS, next startFull feature set, completely portable, no vendorYou run the server, the scaling, and the TLS.
S3 + CloudFront, output: 'export'Cheapest and most bulletproof — it's just filesNo ISR, no API routes, no image optimisation. Content updates require a CI rebuild.
Decision taken

DevOps has not confirmed, but S3 is the expected target — so output: 'export' is the default build, not an afterthought. The more restrictive mode is the default deliberately: anything on the "No" list above now breaks the build on the commit that introduces it, instead of surfacing on launch day. If hosting lands on Vercel or Amplify instead, npm run build:server turns ISR and Route Handlers back on with no source changes.

Proven, not assumed — three real export failures already caught

Running the export build during scaffolding surfaced exactly the class of problem your teamlead has been burned by. All three are fixed in the committed code:

Build errorCauseFix applied
Page "/[slug]" returned an empty array from generateStaticParams() No CMS configured yet, so there were no slugs. Static export requires every dynamic route to produce at least one path. The 13 live slugs are committed in src/content/seed-posts.ts and used until CMS_API_URL is set. Doubles as the canonical list of URLs that must survive the migration.
export const dynamic = "force-static" not configured on route "/sitemap.xml" sitemap.ts compiles to a route handler; because it awaits a fetch, Next treats it as dynamic. export const dynamic = "force-static" in sitemap.ts and robots.ts.
Latent: empty params on /blog/page/[page] Would break the build the moment the blog fits on a single page — a bug that only appears months later. Falls back to one page and renders an empty state instead of returning [].

Also worth knowing: lucide-react v1 has removed its brand icons (Twitter, Facebook, Instagram, YouTube), so the four social marks are inline SVGs in components/layout/social-icons.tsx rather than a dependency that can drop them again.

Static-first rules that keep the S3 escape hatch open

  1. All data access goes through src/lib/api/*. No component ever calls fetch. Switching from fetch-at-build to fetch-in-browser then touches one folder, not forty files.
  2. All form submissions go through src/lib/api/forms.ts, which posts to process.env.NEXT_PUBLIC_FORM_ENDPOINT. Point that at our own /api/contact today, or at Resend / HubSpot / an API Gateway Lambda under static export. The components never know.
  3. One <Img> wrapper around next/image, so unoptimized becomes a single-line change.
  4. Middleware is off-limits for anything the site needs to function. Redirects go in next.config.ts.
  5. Revalidation is centralised in app/api/revalidate/route.ts — one CMS webhook. Under static export the same webhook triggers a CI rebuild instead. Same contract.
  6. Run next build from day one in CI, on every PR. Build breakage found on commit 12 is a ten-minute fix; found on launch day it is a weekend.

Why components/ and features/ are both there

components/ holds things that would work on any site — a Button, an Accordion. features/ holds things that only make sense here — home/sections/Faqs.tsx. Without that split, one components/ folder reaches 90 files by launch and nobody can tell what's safe to change. With it, you always know: touching ui/ affects the whole site, touching features/home/ affects one page.

The seven rules that keep files short

  1. A page file only composes. Imports sections, exports metadata, returns them in order. 20–40 lines, always.
  2. A section file only lays out. It maps over data from content/ or lib/api/. No hard-coded sentences in JSX.
  3. Copy lives in src/content/*.ts as typed arrays. Marketing changes one line in one file and never opens a component. This alone is what keeps section files under 60 lines.
  4. Server Components by default. 'use client' goes on the smallest possible leaf — the accordion, not the section that contains it. Every misplaced 'use client' drags its whole subtree into the browser bundle.
  5. Never fetch in a component. Always through lib/api/. This is rule 1 of Part 03 wearing a different hat.
  6. One component per file, named export, an index.ts barrel per folder so imports read import { Button, Card } from '@/components/ui'.
  7. Absolute imports only — @/features/home/sections/Hero. No ../../../ anywhere; it survives file moves.

Who provides the form endpoint?

Static export has no Route Handlers, so the contact, trial and newsletter forms cannot work on S3 without an endpoint outside this app: API Gateway + Lambda, Formspree, HubSpot, or similar. The code is ready — it reads NEXT_PUBLIC_FORM_ENDPOINT and needs nothing else. Until it's set, submissions log to the console so development isn't blocked.

Ask DevOps for an API Gateway + Lambda, or approve a third-party form service.
OPEN 02

Which CMS, and who publishes?

Headless WordPress is assumed — the 13 posts already live there and editors keep the admin they know. Alternatives are Sanity or Strapi (both need migration), or MDX files if only developers will ever publish. Whichever it is, only src/lib/cms/ changes.

Also confirm that the CMS webhook can trigger a CI rebuild — that's how content goes live on S3.
OPEN 03

Brand palette and fonts?

The site currently runs on shadcn's neutral placeholder tokens and Geist. Replacing them is a single edit to :root in globals.css — no component touches a hex value. Send brand hex codes and font files, or point me at a Figma file and I'll extract them.

Fallback I extract the current theme's colours and type scale from the live site.
OPEN 04

Assets and legal copy?

Section layouts are built with neutral placeholder blocks marked TODO where images go. I need the hero image, student photo, founder portrait, logo and particle SVGs — plus the approved privacy policy and terms copy, which are currently stubs.

Note Record real width/height in src/content/*.ts; static export has no image optimiser to guess for us.

Build order from here

  1. Done — scaffold and shell. Config, data layer, SEO, validation, layout, all 12 routes, and a green npm run verify producing 28 static pages.
